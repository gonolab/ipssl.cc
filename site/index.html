Rules

  • When a name holds more than one address, the rightmost one, closest to the zone, wins.
  • Numbers with leading zeros, such as 010, are rejected, so nobody has to guess whether they are octal.
  • An AAAA query for an IPv4 name, or the other way round, gets an empty answer, not NXDOMAIN.
  • A TXT query for ip.ipssl.cc returns the address the query came from, usually your resolver.

Real certificates, issued to your own server.

The name resolves to your server, so an ACME client running there passes HTTP-01 or TLS-ALPN-01 validation as it would for any other domain. There is nothing to sign up for, and the private key never leaves your machine.

  • Any CA. The zone publishes no CAA record, so Let's Encrypt, ZeroSSL, Google Trust Services and others can all issue.
  • Public addresses only. The CA has to reach your server, so private addresses such as 192.168.1.10 cannot be validated.
  • One shared limit. Every name under ipssl.cc counts toward Let's Encrypt's rate limit for the registered domain. If you hit it, try again later or use another CA.
$ sudo certbot certonly --standalone \
    -d 203-0-113-10.ipssl.cc
$ acme.sh --issue --standalone \
    -d 203-0-113-10.ipssl.cc
# Caddyfile
203-0-113-10.ipssl.cc {
    reverse_proxy localhost:8080
}

Rate limited, never cut off
UDP answers are limited per client network so the servers cannot be used to flood someone else. A resolver that gets a truncated answer retries over TCP, which is never limited.
No query logs
The servers keep aggregate counters only, such as how many A queries they answered. Query names and client addresses are not logged.
Small, written in Rust
An authoritative server built on hickory-dns. Config changes load without dropping a query.

Questions

Something missing? Ask in the issue tracker.

Why doesn't a private address resolve on my network?

Many routers (OpenWrt, pfSense, dnsmasq, Fritz!Box and others) have DNS rebinding protection, which drops answers that point to private addresses. Allowlist ipssl.cc there, or use a public resolver.

Can I download a wildcard certificate for ipssl.cc?

No. Publishing a private key breaks the CA's subscriber agreement, and anyone holding the key could revoke the certificate. Get a certificate on your own server instead; it takes one command.

Why isn't ipssl.cc on the Public Suffix List?

The list excludes services that resolve an IP address written in a hostname to that address: the same IP can belong to different people over time, so it does not show stable control of a name. DNS resolution does not depend on the list.

How do I see where my DNS queries come from?

Run dig +short TXT ip.ipssl.cc. The answer is the address the query reached us from, which is usually your recursive resolver.

Can I run this for my own domain?

Yes. The server is open source under the MIT license, and the install script below sets it up on any Linux server. The README covers the config and the registrar setup.

How do I report abuse?

Email abuse@ipssl.cc or open an issue on GitHub with the name and what it is used for. The server has a blocklist, so names used for abuse can stop resolving.
